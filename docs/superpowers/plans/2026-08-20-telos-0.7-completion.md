# Telos SDD M4–M5 Completion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete Telos 0.7 by closing the remaining configuration and M3 guard contracts, then shipping the read-only live/static view, deterministic rebuild planning and executable progress, GitHub CI generation, and a public reconstruction proof.

**Architecture:** Configuration changes are complete typed staged operations whose canonical before/after bytes are approval-visible and written only by reconcile. Host guards compute decision context from the current repository rather than trusting an agent-supplied description. M4 derives one immutable `ViewSnapshot` from the validated Telos model and project state, then feeds the same escaped HTML renderer to both an Axum loopback server and an atomic static exporter. M5 adds deterministic prerequisite-first rebuild planning in `telos-core`, exposes context-rich plans and real test-run progress through the CLI, generates a version-pinned GitHub workflow, and proves the flow with a spec-only Billing demo that traverses the ordinary Telos change lifecycle.

**Tech Stack:** Rust 2024, clap 4, serde/serde_json, axum 0.8, tokio 1, notify 8, tempfile/assert_cmd for tests, GitHub Actions.

**Spec:** `docs/specs/2026-08-19-telos-sdd-design.md` §§5–12 and 14.

## Global Constraints

- Every shell command is prefixed with `rtk`.
- All public CLI commands preserve the five-key JSON envelope `{ok, command, result, error, next_actions}`.
- The official vocabulary, CLI names, generated text, and Telos data remain English.
- `telos view` is read-only, binds only `127.0.0.1`, and makes no external network request.
- Live and exported pages are Dashboard, Graph, Intent, Glossary, and Coverage; all are cross-linked.
- Static export is self-contained: inline CSS/JavaScript and no external URL, font, image, stylesheet, or script.
- Live view may observe `DRIFTED`; static export refuses `DRIFTED` and `CHANGING` so it is an actual sealed snapshot.
- `rebuild` refuses drift in sealed projects, performs no LLM call, and generates no application code.
- Rebuild order is prerequisite-first according to `requires`, deterministic by intent ID for ties, and includes every intent plus its bounded context pack.
- Rebuild progress means real scenario test outcomes for the current reconstructed tree, not the presence of a stale `proves` binding alone.
- `telos init --ci github` never overwrites an existing owned target and preflights all requested agent/CI integrations before creating `telos/`.
- The generated CI installs the same Telos release from `https://github.com/hugues31/telos-sdd` tag `v${CARGO_PKG_VERSION}` with Cargo `--locked`, then runs `telos check --sealed`.
- Existing M1–M3 JSON contracts, error codes, guards, witnesses, bindings, and acceptance loops remain compatible.
- `telos config` never edits `telos/telos.toml` before approval/reconcile; the staged op itself contains the complete intended configuration and moves the approval digest.
- `[agents] hosts` is sorted/deduplicated project metadata written by `init --agents`; configuration editing preserves that field. Installing or removing host artifacts remains an initialization concern, not an implicit side effect of config reconcile.
- Native decision prompts surface repository-derived current context: the exact change digest for approval and the current drift paths for adopt/revert. Codex combines a dynamic hook `systemMessage` with its static native rule because its documented `PreToolUse` API does not support `permissionDecision: "ask"`.
- No runtime-hosted service, CLI-side LLM call, web editor, semantic merge, or shared-spec registry is added.

- [ ] **Step 4: Support sealed and spec-only rebuild inputs**
