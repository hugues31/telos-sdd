# Architecture

Telos has three layers:

1. The Go CLI owns deterministic IDs, validation, rendering, hashing, state reconstruction, and provider installation.
2. Skills and specialized agents own judgment-heavy work: ideation, ambiguity resolution, specification, adversarial test design, implementation discipline, and independent verification.
3. Git and provider-native hooks provide history and pre-write guardrails.

## Authority and derivation

The authority chain is:

```text
sealed intent
  └── sealed spec(s)
        └── sealed JSON test plan
              └── generated .feature
                    └── active change context
                          └── implementation + verification evidence
```

Markdown artifacts use TOML frontmatter so humans can review them without a custom editor. Machine-oriented data uses JSON. Configuration uses a deliberately small TOML subset to keep the binary dependency-free.

The lock root is SHA-256 over sorted `normalized/path + NUL + artifact hash + LF` records. Text content is normalized to LF. The root is not a full Merkle tree and does not provide signatures; the name “root hash” describes its role as the deterministic digest of the locked set.

## Event ledger

Each event is a separate immutable JSON file. This avoids a shared append target during Git merges. `state.json` projects the ledger for fast inspection, while authoritative verification always recomputes locked content.

## Test generation

The JSON test plan is the reviewed source. `.feature` is a deterministic projection with stable rule and scenario tags. Step definitions remain language/framework-specific application code and are intentionally not generated by the core CLI.

## Provider boundary

Codex and Claude Code receive equivalent Skills and agents through their native repository layouts. Both hook configurations call the same `telos guard` process and consume the common `PreToolUse` JSON shape. Provider adapters contain no integrity logic.
